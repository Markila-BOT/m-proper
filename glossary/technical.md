| Term | Definition | Use When | Avoid |
| --- | --- | --- | --- |
| Dependency maintenance | Keeping declared toolchain dependencies at their current upstream releases without changing product behavior. | Describing version bumps, lockfile refreshes, or dependency removals. | "Upgrade project", "modernize" |
| Baseline capture | Evidence of the pre-change build, runtime, and UI state recorded before the first dependency change. | Describing the first task of a maintenance change or comparing before/after states. | "Snapshot", "pre-check" |
| Live smoke | Exercising the running API and web app against the real Supabase Postgres database. | Verifying behavior that unit tests cannot reach. | "Manual test", "QA pass" |
| Parity audit | A comparison of the post-change UI against the baseline that treats any unexplained visual difference as a regression. | Verifying that dependency updates did not alter rendered behavior. | "Visual review", "screenshot check" |
| Explicit version range | A dependency specifier that names a concrete version constraint instead of a dist-tag. | Recording dependency policy in manifests and ADRs. | "Pinned version" (a range still allows updates) |
| Fenced Gherkin | A scenario whose Given/When/Then steps live in a column-0 ```gherkin fence inside spec.md, making the spec executable source. | Describing spec format under spec-as-source, or authoring spec deltas. | "Cucumber file", ".feature file" (that is generated, never authored) |
| Effective spec | The executable set a suite run loads: every main spec with active change deltas applied, superseded rules excluded without appearing skipped. | Describing what the acceptance suite executes during a run. | "All specs", "the test list" |
| Acceptance suite | The independent cucumber-js project under acceptance-tests/ that boots the app, executes the effective spec, and gates sync/archive on a green run. | Naming the verification instrument in specs, tasks, and summaries. | "test suite", "the tests" (it is one project with one gate) |
| Extraction | The toolchain step that rewrites every spec.md under openspec/ into .feature files with identical line numbers, hard-erroring on unfenced scenarios. | Explaining why unfenced specs block the suite, or where a lint error points. | "conversion", "parsing" |
| Running balance | A money column that accumulates down the ledger in displayed order, derived client-side from the transactions on the page, with no opening-balance concept. | Describing the passbook ledger's signature column or its steps. | "Total", "sum" (single aggregates, not an accumulating rail) |
| URL as state | The navigation model where each ledger view has a real route and the browser URL carries the app's location, replacing in-shell tab state. | Describing the routed shell or the redirect at '/'. | "Deep-linking" alone (a consequence, not the model) |
| Payment reminders API | The Axum routes and Supabase tables that store payment labels, reminders, and occurrences. | Naming the server-side surface. | "Reminder backend" |
| Materialized occurrence | A stored occurrence row generated by the API from a reminder's rule, so amounts and status can be edited and audited. | Explaining why occurrences are rows, not computed on read. | "Generated dates" |
| Occurrence horizon | The date span the API generates occurrences for: the start date through an end date, or a bounded future window for an open-ended reminder. | Describing the generation bound. | "Regeneration window" |
| Ledger link | The occurrence field holding the local transaction id of the linked expense; the ledger itself stays client-side. | Describing the cross-store link. | "Foreign key" (the ledger is not in Postgres) |
| Cascade deletion (payment history) | Deleting a property deletes its payment reminders and occurrences, with the UI warning before the act. | Describing the chosen property-deletion behavior. | "Soft delete" |
| Local-Date Rule | Every user-visible date derives from local calendar parts, never a UTC instant: stored dates are `YYYY-MM-DD` calendar strings, and `toISOString` is never used for display. | Describing date parsing, formatting, or storage. | "UTC date" |
| Pointer affordance | The cursor and hover feedback that tell a pointer user a control is interactive. | Describing cursor or hover behavior. | "Hover effect" alone (it is both) |
| Hover-capable pointer | A primary pointer that can hover, such as a mouse or trackpad, as distinct from touch. | Describing `@media (hover: hover)` gating. | "Desktop" |
| Coarse pointer | A touch-style primary pointer that cannot hover. | Describing touch behavior. | "Mobile" |
| Access token | The short-lived Supabase Auth JWT the app verifies from the session cookie. | Describing the credential the routes verify. | "Session token" |
| Refresh token | The long-lived credential the web rotates to obtain fresh access tokens. | Describing session renewal. | "Access token" (different lifetime) |
| JWKS | The project's public JSON Web Key Set used to verify access tokens without the Auth server in the hot path. | Describing token verification. | "Public key" (one key of the set) |
| Identity | The verified caller (`sub`, email, role) extracted from the access token. | Describing the authenticated principal in the routes. | "User" (the database row) |
| Server route | An HTTP handler the app's file router owns, serving the properties JSON on the app's own origin (`/api/...`). | Describing an app-owned endpoint. | "API server" (there is no separate server) |
| Session cookie | The Supabase session the browser sends to the app's own origin (`sb-<ref>-auth-token`, base64url JSON, chunked when large). | Describing how the routes learn who is calling. | "Auth header" (the withdrawn transport) |
| Cookie contract | The rules a route applies to that cookie: name derivation, chunk assembly, and a malformed cookie answering 401 rather than throwing. | Describing cookie parsing obligations. | "Cookie parsing" (too vague) |
| Frozen baseline | The migration that reproduces the schema already applied by the previous migration tool and is recorded as applied rather than run as new DDL. | Describing the Drizzle cutover. | "Initial migration" (it must not re-create tables) |
| Direct connection | The non-pooled Postgres URL used only by the migrate step. | Describing migration connections. | "Pooled connection" (the app's runtime connection) |
| CSRF check | The rule that a state-changing request's `Origin` or `Sec-Fetch-Site` is the app's own, required because the credential is an ambient cookie. | Describing write protection. | "CORS" (never protected the server) |
| Owner ID | The `auth.users.id` stored on a row, the database half of the owner scope. | Describing row ownership. | "User ID" (ambiguous with the caller) |
| RLS defense | Row Level Security policies as a second authorization layer; a privileged API connection bypasses them. | Describing defense in depth. | "RLS" alone (it is the second layer) |
| Test identity | The dedicated Supabase user the acceptance suite signs in as. | Describing the verification setup. | "Test user" |
| Local ledger scope | The browser transaction storage keyed per landlord account so accounts on one device cannot see each other's entries. Deferred to `server-transactions`, which retires the local ledger (ADR-0009). | Describing local privacy. | "Shared ledger" |
| Transaction API | The owner-scoped Axum routes and Supabase table that store ledger entries. | Naming the server ledger. | "Ledger backend" |
| Ledger restore | The undo path that re-creates a deleted entry with its original id inside the undo window. | Describing the delete undo. | "Undelete" |
| Ledger discard | The one-time retirement of the browser ledger with no server import. | Describing the migration decision. | "Migration" (there is no data migration) |
